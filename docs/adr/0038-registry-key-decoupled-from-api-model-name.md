# Modelo multimodal anfíbio: chave alias no registry + `api_model_name` desacoplados; sem chave composta `(model_id, media_type)` no registry

`PROVIDER_REGISTRY[provider].models` usa string model_id como chave única; um model_id corresponde a um `ModelInfo`, um `media_type`. Essa chave acumula três cargos: **identidade de UI / persistência** (seletor de modelo no frontend, `"model"` em `project.json`, coluna `ApiCall.model`, body de request de API — todos o mesmo string nu), **chave de lookup de cobrança / capacidade** (`lib/pricing/lookup.py` e buscas de capacidade batem nela com precisão) e **nome de modelo enviado à API do provider**. Os três cargos compartilham um string globalmente único e se rompem no «modelo multimodal anfíbio»: imagem e vídeo do Kling v3-omni na API Kling **se chamam ambos `kling-v3-omni`**, mas uma chave com um único `media_type` não acomoda duas entradas de modal com o mesmo nome de API.

Decidimos **adicionar a `ModelInfo` o campo `api_model_name: str | None = None`** (default `None` recua para o nome da chave; entradas legadas zero impacto), separando o cargo «nome de API enviado ao provider» do cargo «chave única interna»: a entrada de imagem usa a **chave alias** `kling-v3-omni-image` (`api_model_name="kling-v3-omni"`); a chave primária `kling-v3-omni` fica com o vídeo; o backend de imagem envia `api_model_name or nome da chave` (o backend de vídeo, com a única entrada anfíbia na chave primária e o nome da chave já sendo o nome de API, por ora sem necessidade de alias, ainda envia o nome da chave direto); cobrança e lookup de capacidade continuam pela chave do registry. O `display_name` de cada entrada se distingue («可灵 V3-Omni（图像）」/ «可灵 v3 Omni»); a chave sintética não vaza para a UI.

**Explicitamente não adotamos**: mudar a chave do registry para o composto `(model_id, media_type)`. A chave composta de fato casa melhor com a realidade no nível do registry (um modelo de API, dois modais = duas linhas com o mesmo model_id, sem chave alias nem `api_model_name`), mas mexe nos dois primeiros cargos do model_id que **não** estão em conflito: model_id é **token de identidade cross-camada**; seleção no frontend / `project.json` / `ApiCall.model` / body de API / lookup de pricing são todos **string nu sem `media_type` ao lado**. A chave composta empurra o custo para todas essas fronteiras — em especial o snapshot de custo (`docs/adr/0009`) no instante do finish só tem a string do modelo; linhas históricas de `ApiCall` não recuperam `media_type`; o dict de taxas dentro do módulo de pricing também é chaveado por string de modelo e seria forçado a composto. O anfíbio só conflita no cargo «nome de API» do model_id; cobrar imposto de chave composta em todo o sistema por um único modelo anfíbio no registry inteiro é desproporcional. Princípio: **desacoplar só o cargo em conflito; não mexer nos dois que não atrapalham.**

## Consequences

- **Compatibilidade retroativa**: modelos legados `api_model_name=None` recuam ao nome da chave, zero mudança de comportamento; modelo não-anfíbio novo não precisa se importar com o campo.
- **Adaptação de backend assimétrica**: hoje só o caminho de imagem consome `api_model_name` (`KlingImageBackend` recebe o parâmetro e envia o nome de API com base nele); o backend de vídeo ainda não tem parâmetro `api_model_name` e envia o nome da chave. Hoje não atrapalha — o lado de vídeo da única entrada anfíbia v3-omni ocupa a chave primária e o nome da chave é o nome de API; mas se no futuro um modelo anfíbio precisar que a entrada de **vídeo** use chave alias, o backend de vídeo precisa ganhar suporte a `api_model_name` antes, senão envia o nome da chave por engano. Isso é trabalho prévio do «gatilho de refatoração» abaixo.
- **Sabor de chave sintética aceito de forma explícita**: `kling-v3-omni-image` é identificador interno do registry que não existe no mundo do provider; se explica por este ADR + blindagem de `display_name`, sem tratar como chave morta a limpar.
- **Gatilho de refatoração**: quando modelos multimodais anfíbios se multiplicarem e o padrão «chave alias + `api_model_name`» incomodar o suficiente, reavaliar chave composta `(model_id, media_type)` ou outra cura raiz — aí a refatoração tem base e este ADR vira superseded.
- **Convergência da mesma família**: herda `docs/adr/0009` (pricing entra em `ModelInfo`, lookup por chave) e `docs/adr/0013` (declaração de capacidade converge no nível do modelo) — os três respondem «o que a chave do registry / `ModelInfo` carrega». Este ADR é a terceira separação de responsabilidade da chave do registry: tira «nome de API externa» de «chave única interna».
