# Após restart, tarefas órfãs nunca re-disparam geração; tipo submit-poll retoma poll por job_id

Em `generation_worker.py`, quando o worker obtém o lease e a instância não tem tarefa em voo, chama `requeue_running_tasks()`, devolvendo ao queued todas as tarefas órfãs com `status='running'` no DB (sem asyncio.Task correspondente na memória do worker; a única causa realista é restart do processo do serviço — deploy ou recuperação de crash) para o próximo claim reexecutar. Em sistema de «serviço externo reentrante, cobrança por duração» isso é self-heal razoável; no ArcReel não: o custo de geração de mídia é cobrado por **número de chamadas à API do provider**; cada requeue cobra de novo; e uma única geração de video vai de centavos a vários reais — um pico de restart (janela de deploy, OOM do container) pode reexecutar dezenas de tarefas running do projeto. Em um incidente real de usuário em 2026-05-24, o pool custom-11 video (capacidade 3) ficou cheio com 3 long-polls Sora e, combinado ao bug de design de cancel running não interromper asyncio.Task (ver `docs/adr/0006-cancelling-intermediate-state.md`), o projeto inteiro travou; se o usuário tivesse reiniciado na hora, seriam três cobranças duplicadas.

Decidimos: tarefas órfãs **nunca** disparam geração de novo automaticamente. O padrão é marcar status `failed` com error_message «interrompido por restart do serviço», e o usuário decide se reenvia. Mas para backends de **video do tipo submit-poll** (video de Gemini/Ark/OpenAI/Vidu/NewAPI — chamada = «submete job uma vez + depois polla job_id pelo resultado»), oferecemos capacidade de «retomar poll»: a tabela Task ganha coluna `provider_job_id` (migração alembic); cada video backend, após submit, persiste o job_id na task correspondente; no start, o worker varre a tabela e, para órfãs com job_id, chama a nova interface `resume_video(job_id)` do backend e continua o poll, sem re-submit. Sem job_id (backend síncrono, ou processo morreu antes do submit), backend sem resume, ou provider devolvendo job expirado/unknown — marca failed, com error_message `[restart_lost]` / `[resume_unsupported]` / `[resume_expired]` para distinguir. **Tarefas de image estão fora do escopo de resume deste ADR**: a maioria dos backends de image é síncrona (request-response; HTTP cai, perdeu); poucos como image de Vidu/NewAPI também são poll-based, mas a tarefa de image é curta e o ganho de resume é pequeno — YAGNI; essas órfãs de image vão unificadas no fallback «marca failed → usuário reenvia manualmente».

## Consequences

- O ponto de chamada de `requeue_running_tasks()` some do loop principal do worker; o corpo da função permanece para testes unitários ou resgate manual futuro. No start, o worker passa a `_handle_orphan_tasks_on_start()`, despachando pela estratégia acima: retomáveis retomam poll; o resto marca failed.
- «Retomar poll» precisa de colaboração do backend. A classe abstrata `VideoBackend` ganha o método opcional `async def resume_video(job_id: str) -> ...` (default lança `NotImplementedError`). Backends submit-poll reutilizam o `_poll_until_complete` existente, só mudando a entrada de «chamar após submit» para «chamar direto com job_id» — a lógica principal não se reescreve. Backends síncronos (image/video Grok, e image de Gemini/Ark/OpenAI) não implementam; órfã → failed direto.
- Visão do usuário: após restart, tarefas de video em geração (quase todas poll) continuam sozinhas, sensação zero; tarefas de image em geração (quase todas síncronas) viram failed e o usuário reenvia manualmente. Este escopo não faz UI de retry (já confirmado); o «reenviar» do usuário é o caminho existente «clicar gerar» — trade-off consciente para manter o PR em «consertar paralisia da fila» em três frentes.
- Este ADR combina com o fato de que «GenerationWorker e o processo principal do server sempre estão amarrados» (termo `worker` em `CONTEXT.md`): com um único processo uvicorn, a única origem de órfã é restart; sem coordenação multi-worker, não há «órfã falsa» por jitter de lease/heartbeat (lease caiu mas o processo ainda está vivo). Se no futuro houver multi-worker de verdade, a estratégia precisa de reexame — em concreto, distinguir «órfã do processo que acabou de subir» (ninguém está rodando) de «órfã ainda viva em outro worker» (ainda há asyncio.Task na memória do outro processo). Este ADR não reserva lógica de julgamento para esse futuro.
- Órfãs com `status='cancelling'` no restart (serviço reiniciou no meio do encerramento de cancel running) marcam `cancelled` direto: o usuário já expressou vontade de parar via API de cancel; continuar o poll até success e cancelar de novo não faz sentido. Isso é ramo independente de «órfã running → failed/resume» — cancelling e running são estados distintos na máquina; órfã cancelling não consome o protocolo de resume nem a semântica de custo.
- Não se sobrepõe nem conflita com `docs/adr/0006-cancelling-intermediate-state.md`: 0006 cobre «como tarefa em execução é interrompida de fora»; 0007 cobre «como tratar tarefas ainda não mortas após restart». Cancel running passa pelo intermediário cancelling; órfã de restart vai failed ou resume, **sem** passar por cancelling (cancelling é vontade subjetiva do usuário; restart é evento de sistema).
- Não volte a requeue «para o restart parecer mais transparente»: isso transforma o modelo de custo de «cobrança por chamada» em «chamadas × restarts», o usuário perde na fatura, e o ponto de proteção de semântica de custo deste ADR morre.
- A persistência de `provider_job_id` deve **completar de forma síncrona antes de entrar no poll** — se `submit` já devolveu job_id mas a escrita no DB falhou (I/O SQLite, conexão cortada), a task deve marcar `failed` na hora e **não** entrar no poll. Senão o job continua cobrando no provider e o ArcReel não consegue resume (job_id não gravado) nem cancel (worker não sabe que a task ainda roda), formando «tarefa fantasma» não rastreável. Caminho de implementação: após `submit`, commit do job_id em transação própria; falha do commit lança e o finally do worker marca failed; só com commit ok entra no loop `_poll_until_complete`.
- O caminho fail-fast deve ser **observável**: o ramo «marca failed» por falha de persistência de `provider_job_id` precisa de log estruturado (task_id / provider / job_id devolvido pelo submit / motivo do erro) + um contador de métrica (nome da metric fica para o PR de implementação). Senão ops não separa «proteção de tarefa fantasma disparou» do ruído de «falha normal de provider» — regressões de deploy (I/O intermitente no DB) ficariam silenciosas, exatamente o modo de falha que esta proteção evita.
