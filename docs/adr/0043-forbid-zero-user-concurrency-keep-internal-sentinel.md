# Teto de concorrência: proibir 0 como input do usuário (≥1 ou vazio); 0 só como sentinela interna de lane não suportada

`0` no sistema de concorrência acumulava dois papéis em conflito: por dentro, CapacityTable trata capacidade `0` de uma lane como sentinela «este provider não suporta esta mídia» (`_lane_limits` projeta lanes não suportadas em `0` por `media_types`; o worker com `if cap <= 0` faz fast-fail `mark_failed("provider_unsupported_media")`); já os campos de teto de concorrência configuráveis pelo usuário (embutido via `_validate_value`, custom via API `ge=0` + DB `CHECK >= 0`) antes **aceitavam** `0` sem distinção. Usuário preenchendo `0` (lendo mal o placeholder «default», ou achando que `0`=ilimitado) desligava a lane em silêncio, e cada tarefa seguinte reportava «provider não suporta esta mídia» — footgun silencioso com mensagem de falha que não responde à pergunta. O default de fábrica do registry `ProviderMeta.default_concurrency` já exige `>= 1`; só o valor do usuário liberava `0` — assimetria dos dois lados.

Decidimos **remover `0` do input legal do usuário**: todas as camadas de input do usuário (formulário frontend, API de custom provider `Field(ge=1)`, `_validate_value` embutido com `parsed < 1`) e o DB CHECK (três colunas de `custom_provider` `>= 1`) exigem unificadamente `>= 1`; vazio / `NULL` ainda significa «recuar ao default». `0` só permanece como sentinela interna de CapacityTable «lane não suportada», fechada ao usuário. Como o lançamento de concorrência de custom provider (ADR 0042) ainda não publicou, o aperto do DB CHECK **reescreve direto a migração de adição de coluna** (`>= 0` → `>= 1`, nome da constraint `_non_negative` → `_positive`), sem migração nova nem backfill de dados (`0` não tem origem automática; a única origem é input do usuário — bloquear na porta e deixa de nascer). O runtime `if cap <= 0` / `_lane_limits` / `provider_unsupported_media` não se mexe — daí em diante `0` só pode vir de «este provider de fato não suporta esta mídia»; a semântica do código de falha fica exatamente correta.

**Explicitamente não adotamos**: elevar `0` a cidadão de primeira classe «desabilitar esta lane». O provider se vincula no enqueue; `0` não redireciona a tarefa a outro provider, só faz fast-fail — não implementa «desabilitar com elegância»; o fallback em três camadas já usa vazio / `NULL` com limpeza para «usar o default»; `0` não precisa de segunda semântica; o jeito honesto de não querer um provider em certa lane é não escolhê-lo para essa lane. Se no futuro «desabilitar certa lane de certo provider» for necessidade real, deve haver switch explícito com código de falha honesto, não sobrecarregar `0`.

## Consequences

- **Os dois papéis de `0` se separam de vez**: a face de contrato do usuário «teto de concorrência é inteiro ≥1 ou vazio» e a interna «capacidade `0` = lane não suportada» não compartilham mais o mesmo valor alcançável pelo usuário; a entrada «capacidade» de CONTEXT.md ganha o contrato do usuário em sincronia.
- **Reescreve migração já mergeada em main**: outros worktrees / DBs de dev que já rodaram `alembic upgrade head` na versão antiga (`>= 0`) não apertam o CHECK sozinhos (alembic não re-roda revision já aplicada) — precisam de `downgrade -1 && upgrade head` ou recriar o DB de dev. Como não publicou e `0` não tem origem automática, na prática é inofensivo; é trade-off deliberado de «migração não publicada pode se reescrever in-place» — depois de publicar, essa técnica não se reutiliza.
- **Mudanças convergem**: validação nas três camadas de input + CHECK DB nas três colunas + aperto in-place da migração original + textos i18n (backend `max_workers_must_be_positive_integer`, frontend «inteiro positivo» e texto de ajuda) + testes correspondentes. Agendamento de runtime, SlotTable, isolamento de lane e reload não se mexem.
- **Mantém a fronteira**: unifica com a regra `default_concurrency >= 1` do registry; herda ADR 0042 (colunas tipadas de concorrência de custom provider).
