# Modelo de credenciais de custom provider fixo em `api_key` + `base_url`; protocolos de credencial multi-campo só via provider embutido

O ORM `CustomProvider` do ArcReel (`lib/db/models/custom_provider.py`) hoje expõe só dois campos de credencial por provider criado em runtime pelo usuário: `api_key` (string única, mascarada por `mask_secret`) + `base_url` (entrada HTTP). Pesquisa paralela de adaptação de protocolos de API de vídeo encontrou vários protocolos de «credencial nativa multi-campo»: Kling oficial usa JWT HS256 (`access_key` + `secret_key`, token expira em 30 min), Vertex AI Veo usa arquivo JSON de service account (`credentials_path`, mais project_id / OAuth2 scopes), visual.volcengineapi.com da Volcano usa AKSK + canonical request + assinatura HMAC. Se esses protocolos fossem expostos como endpoint para custom provider no estado nativo, o modelo de credenciais do CustomProvider teria de virar multi-campo (candidatos: novo campo `extra_credentials: JSON`, ou campos dedicados `api_secret` / `service_account_json` etc.).

Decidimos **não** estender o modelo de credenciais de custom provider. `CustomProvider` fica de longo prazo com `api_key` de um campo + `base_url`; qualquer protocolo de «credencial nativa multi-campo» **só** entra via provider embutido (`PROVIDER_REGISTRY.required_keys: list[str]`, já multi-campo; ex.: `gemini-vertex.required_keys=["credentials_path"]`, Kling planejado `required_keys=["access_key","secret_key"]`). O caminho de compatibilidade para o usuário que chega a multi-campo por um relay é o **relay fazer protocol translation** — o relay resolve a autenticação multi-campo no próprio servidor e expõe Bearer `api_key` + `base_url` do relay (evidência: relays Kling em geral usam o path `/kling/v1/videos/{text2video|image2video|multi-image2video}` repassando o schema nativo Kling, mas a auth colapsa em uma única chave Bearer). O que o closure do endpoint enxerga é sempre um único api_key. Essa é a fronteira de desacoplamento entre modelo de credencial e forma do protocolo.

## Consequences

- **Modelo de credencial não se contamina com a forma do protocolo**: schema de CustomProvider, Repository, caminhos de `mask_secret`, armazenamento cifrado, formulário de credenciais na UI (página de settings «adicionar custom provider»), `/api/v1/custom-providers/discover` — nenhum introduz caso especial de «credencial multi-campo». Cada novo protocolo nativo multi-campo (Kling, Vertex, AKSK, provider futuro) também não toca essa cadeia inteira — o ponto de extensão de adaptação de protocolo converge nas implementações de backend em `lib/video_backends/`, `lib/image_backends/`, `lib/text_backends/` e no registro `ENDPOINT_REGISTRY`; a camada de credencial fica estável.
- **A mesma implementação de backend pode carregar dois modos de credencial**: exemplo típico é `KlingVideoBackend` (a implementar) suportando ao mesmo tempo o modo JWT (provider embutido `kling-official`, construtor recebe `access_key + secret_key`) e o modo Bearer (closure do endpoint `kling-proxy-video`, só `api_key + base_url`), compartilhando o mesmo schema de body de request e o mapeamento de máquina de estados. É o mesmo padrão do dual mode `backend_type=aistudio|vertex` já existente em `GeminiVideoBackend` (`lib/video_backends/gemini.py`): o backend é o portador da forma do protocolo; o modo de auth é parâmetro de construção.
- **Protocolos que não se proxyam nunca aparecem no dropdown de endpoint**: Vertex AI Veo (arquivo JSON de service account não redireciona base_url para relay), CV visual Volcano (assinatura estilo SigV4 em geral não é reencaminhada crua pelo relay e é reembalada no protocolo NewAPI) etc. ficam ausentes na UI de custom provider. Trade-off consciente — se o usuário realmente precisa, usa provider embutido.
- **Mecanismo futuro de plugin deve manter essa restrição**: quando o plugin runtime aterrissar (ver `docs/research/arcreel-video-api-protocol-research.md` §7.5), o endpoint de plugin também só aceita `api_key` + `base_url`; se o plugin quiser expor protocolo multi-campo, precisa trazer declaração no estilo «provider embutido» (e esse caminho equivale ao plugin estender PROVIDER_REGISTRY — complexidade sobe muito; este ADR não pré-especifica). A restrição mantém a superfície da interface de plugin estável.
- **CONTEXT.md já incorpora o princípio no glossary** (segunda frase da entrada «custom provider»); este ADR dá o porquê de não estender o modelo de credencial, complementando o «o que é» do glossary. Qualquer PR futuro que queira exceção (campo JSON de credencial, secondary key) precisa deprecar este ADR primeiro.
- **Não contornar a restrição «concatenando string com separador dentro de api_key»** (ex. `api_key="access_key:secret_key"` e o backend desmonta). Isso quebra a semântica de exibição de `mask_secret` para chave única, impede a UI de saber qual trecho é o secret de verdade, e mistura lógica de parse de string no backend, borrando a fronteira entre «estrutura do protocolo» e «expressão da credencial». Se um cenário de usuário realmente precisar de exceção, o caminho certo é escrever um provider embutido novo, não hackear o closure do endpoint.
- **Este ADR alinha o estilo de `docs/adr/0001-image-capability-resolved-at-execution.md`**: deixa clara a fronteira «determinado em runtime vs declarado no start» — a forma da credencial se declara no registro do provider (`PROVIDER_REGISTRY.required_keys`), não se estende dinamicamente no request. O endpoint se constrói em runtime, mas a forma da credencial é restrição estática de ENDPOINT_REGISTRY + schema de CustomProvider.
