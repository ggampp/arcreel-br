# Teto de concorrência de custom provider: colunas tipadas nomeadas por lane; sem JSON / kv / subtabela

O teto de concorrência de provider embutido já passa pelas chaves de config `image_max_workers` / `video_max_workers` / `audio_max_workers` de `provider_credential` / `ProviderConfig`, carregadas por `CapacityTable.from_db` e projetadas em tabela de capacidade por lane. Custom provider (tabela `custom_provider`, id em runtime como `custom-{id}`) antes em `from_db` sempre recebia o default global — o usuário não podia limitar a concorrência de um custom provider individualmente, assimétrico em relação ao embutido.

Decidimos **adicionar à tabela `custom_provider` colunas tipadas nomeadas por lane** `image_max_workers` / `video_max_workers` / `audio_max_workers` (Integer nullable); `NULL` significa «não definido → default global». Ao carregar custom provider, `CapacityTable.from_db` lê coluna a coluna; `NULL` recua ao default global (substitui a lógica anterior de sempre aplicar o default global); a projeção continua em `_lane_limits`, reutilizando a semântica estabelecida pelo slice de fallback em três camadas. Custom provider não está no registry embutido `PROVIDER_REGISTRY`, não tem a camada intermediária «default declarado pelo provider», logo o fallback é de duas camadas (valor de coluna do usuário → default global), não as três do embutido. **Explicitamente não adotamos**: ① coluna JSON genérica `extra` (exigiria pipeline de read-modify-write e validação por campo; campo único com RMW concorrente é complexo; ADR 0016 já rejeitou; neste cenário só três tetos escalares não compensam); ② tabela de config KV (config de custom provider não entra no sistema KV de provider predefinido de `ProviderConfig`; reutilizar abriria exceção no resolver e contornaria a única verdade desta tabela); ③ subtabela de campos de concorrência (uma tabela + join por três tetos escalares — volume mecânico máximo).

É trade-off YAGNI: hoje só três tetos inteiros de lanes fixas; o conjunto de campos é estável e simétrico ao embutido; coluna tipada é direta, indexável, migração mínima — isomorfo a ADR 0037 (colunas tipadas multi-secret de provider embutido): o mesmo «quando o conjunto de campos é conhecido e estável, preferir coluna tipada; deixar JSON / subtabela para cenários de verdade dinâmicos».

## Consequences

- **Colunas esparsas aceitas de forma explícita**: as três colunas são `NULL` para custom providers sem concorrência configurada (a maioria das linhas); se explica por este ADR e pelo comentário de fallback em duas camadas de `from_db`, sem tratar como campo morto a limpar.
- **Gatilho de refatoração**: quando custom provider precisar de concorrência per-model, ou a dimensão de lane sair de três fixas para extensível dinamicamente, reavaliar upgrade para coluna JSON `extra` ou subtabela de campos de concorrência — aí a refatoração tem base e este ADR vira superseded.
- **Mudanças convergem**: modelo + uma migração additive de colunas nullable (sem backfill; as três colunas não entram em nenhum `WHERE`); `CustomProviderRepository.create_provider` / `update_provider` repassam; schema CRUD (body POST/PUT + eco na resposta); fiação de custom provider em `CapacityTable.from_db`; três inputs number opcionais no formulário da página de settings. Não mexe no ledger de ocupação SlotTable, isolamento de lane nem mecanismo de reload; não introduz concorrência per-model.
- **Mantém as fronteiras existentes**: herda o slice de fallback em três camadas (custom provider é o caso especial de duas camadas) e ADR 0037 (coluna tipada quando o conjunto de campos é estável). Qualquer PR futuro que queira JSON / kv / subtabela precisa deprecar este ADR primeiro.
