# Fonte de roteiro (source_kind=screenplay): extração prioritária reutilizando a pipeline inteira; fidelidade literal só âncora conteúdo audível

O modo drama espera que o arquivo-fonte seja romance; três trechos de LLM (plan_episodes com split semântico / step1 adaptando para tabela de cenas / step2 reescrevendo para JSON) **criam** o roteiro a partir de prosa; mas há usuários que enviam roteiro acabado com episódios, cenas, falas, voiceover e personagens já feitos, e a pipeline «estilo adaptação» o **reescreve de novo** — plan_episodes recorta os episódios do autor, step1 adapta falas, voiceover some por inteiro. Decidimos adicionar `source_kind` no nível do projeto (`novel` default / `screenplay`) como terceiro eixo ortogonal a content_mode e generation_mode — «natureza do arquivo-fonte» — **fixado na criação, depois imutável** (mesma natureza de content_mode); sob `screenplay` a pipeline drama inteira vira de «criação» para «extração prioritária», e a fidelidade literal só âncora «conteúdo que se ouve».

Extração prioritária **não inventa outro parser de roteiro**; estende cada estágio existente de analyze-assets / plan_episodes / normalize-drama-script — o LLM usa primeiro o que o autor já escreveu (qualquer forma, sem regex de marcadores hardcoded); só gera o que faltar; casa com a arquitetura existente de «consumo preguiçoso por episódio» (script pode ter 100k chars), reutiliza subagent/skill prontos, e cada estágio degrada sozinho (tem tabela de personagens sem marca de episódio → extrai personagens literalmente + planeja episódios semanticamente). **Split de episódios nunca é mecânico**: plan_episodes continua planejamento semântico; se o roteiro já traz episódios (qualquer forma), usa suas fronteiras/títulos/hooks/outlines; se não, escolhe pontos de corte por arco de enredo completo — o ponto de corte é crítico; cortar por comprimento quebra arcos. **Fidelidade literal só âncora «conteúdo que se ouve»**: o que não se reescreve/não se perde/não se polui é só texto de fala de personagem e texto de voiceover; layout/rótulos, direção de câmera e indicações de palco, descrição visual, figurantes genéricos ficam a cargo do LLM reescrever ou descascar (literal rígido enfiaria indicação de palco, figurante e símbolo de layout à força em campos estruturados).

Sob screenplay, falas e voiceovers extraídos literalmente caem em `DramaScene.utterances` (fala `kind=dialogue` com speaker, voiceover `kind=voiceover` sem speaker, na ordem de aparição; modelo em ADR 0040), sem reescrever, sem perder, sem polir. Speaker genérico (`老人甲`) não se registra como asset character nem entra em characters_in_scene; o speaker da fala preenche o tratamento do original, mas não vira asset de personagem — genérico vs nomeado é julgamento do LLM na camada de prompt (`speaker ∈ characters_in_scene` é só instrução de prompt em `prompt_builders_script.py`, sem validação mecânica; sob screenplay essa instrução se afrouxa). O esqueleto extraído (episódios + personagens) passa pela confirmação por estágio já existente de `/manga-workflow` + revisão em lote plan/replan, cobrindo erro de julgamento do LLM em formatos selvagens, zero mecanismo novo. «Dublagem de voiceover/fala» (drama-TTS) é fase de dublagem/síntese, item futuro à parte.

## Considered Options

- **Um parser monólito dedicado**: enfiaria 100k chars em uma chamada, adiantaria todo o trabalho para o upload, confrontaria a arquitetura de «consumo preguiçoso por episódio», e hipóteses de estrutura hardcoded para formatos mil quebram fácil; «extração prioritária sobre os estágios existentes» deixa cada estágio reconhecer semanticamente com LLM no próprio slice e completar o que falta sozinho.

## Consequences

- Validador de dados (`lib/data_validator.py`): validação de enum do campo de topo `source_kind` (só `novel`/`screenplay`; bloqueia valores ilegais como `screen_play`); a validação mecânica de speaker pode afrouxar — a restrição é só instrução de prompt (ver item abaixo).
- prompt builders (`lib/prompt_builders_script.py`): ramos screenplay em plan_episodes / normalize / drama (criação→extração); o ramo drama afrouxa a instrução «speaker deve aparecer em characters_in_scene» para acomodar speaker genérico.
- Assistente de criação + frontend: expõe escolha de source_kind (referência de produto «enviar roteiro / IA gera roteiro»), fixado na criação; tipo `ProjectData` do frontend ganha `source_kind` em sincronia.
- «Dublagem de voiceover/fala» (drama-TTS) é item futuro independente, fora do escopo desta decisão.
