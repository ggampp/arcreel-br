# Construção de backend de provider embutido converge em tabela declarativa; simétrica à tabela de endpoint custom, sem fundir

A construção de backend de provider embutido (montar kwargs de construção a partir de provider config + model resolvido) hoje se escreve de forma imperativa em três pontos de `server/services/generation_tasks.py` — `_get_or_create_video_backend` / `_get_or_create_image_backend` / `_get_or_create_audio_backend` — e em `lib/text_backends/factory.py`, cada um com `if gemini / elif kling / else`; o conhecimento per-provider vaza todo para o caller — dual mode `aistudio|vertex` do gemini, dual secret JWT + desacoplamento `api_model_name` do kling, prioridade de base_url de cada um e texto dashscope/minimax via OpenAI-compat etc. espalhados nesses quatro ramos. O mapa `PROVIDER_ID_TO_BACKEND` ainda existe em duas cópias (lado mídia e lado texto) e já drena: o lado texto trata dashscope/minimax como `openai`; o de mídia não. Já o lado de custom provider usa há tempo `ENDPOINT_REGISTRY` em `lib/custom_provider/endpoints.py` (cada `EndpointSpec` carrega um closure `build_backend`) + `factory.py` em duas linhas de encaminhamento, a mesma coisa como tabela declarativa profunda. Duas formas paralelas — a duplicação rasa (shallow duplication) que esta decisão elimina.

Decidimos elevar o lado embutido ao mesmo nível do custom e convergir para uma costura (seam) «provider config + model → backend»: ① criar `lib/backend_assembly/` (em lib — a costura cruza as famílias embutida+custom, e lib não pode importar server), expor a entrada unificada `assemble_backend(provider_id, media_type, model_id, ...)`, por dentro bifurcando por `is_custom_provider` para os dois adaptadores de família; ② no lado embutido, uma nova tabela `(provider_id, media_type) → ProviderSpec`, cada entrada com um closure de build, isomorfa ao `EndpointSpec` do lado custom; ③ a construção se parte em **carga async** (consulta DB/config, produz o envelope `LoadedConfig`: overlay de credencial + meta de `PROVIDER_REGISTRY` + rate_limiter compartilhado) / **construção sync** (closure puro lê o envelope e monta o backend) — o trecho sync é o núcleo do módulo profundo unit-testável sem DB; ④ o `ENDPOINT_REGISTRY` do lado custom não muda uma linha; a lógica de carga DB de `_create_custom_backend` desce de server para lib e unifica com a cópia inline no text factory.

**Explicitamente não adotamos**: ① **fundir as duas famílias em uma tabela** — os modelos de credencial dos dois lados são essencialmente diferentes (custom fixo `api_key`+`base_url`, ver `docs/adr/0008`; multi-secret embutido em colunas tipadas, ver `docs/adr/0037`), e `EndpointSpec` ainda carrega campos de catálogo do frontend (video caps, request path, display name) que o lado embutido não precisa; fundir ou perde tipo ou enfia `Any`. Duas tabelas compartilham uma entrada (`assemble_backend`), não a estrutura da tabela — uma porta, dois cômodos simétricos atrás. ② **Introduzir value object unificado `BackendRequest` de entrada** (achatar as duas formas de input para a entrada única aceitar um só parâmetro) — não tem segundo consumidor; é só cola para as duas assinaturas de build parecerem iguais; o teste de deletar fura: apagar não reaparece complexidade no caller (o caller já bifurca em `is_custom_provider`), e ainda forçaria num tipo só os dois modelos de credencial que 0008/0037 deliberadamente separaram. Build embutido come `LoadedConfig`, build custom come `CustomProvider`, cada um o seu. ③ **Spec embutido como especificação de dados puramente declarativa** (tabela de mapeamento de credencial + enum de política de base_url no lugar de closure) — over-config para ~11 providers embutidos atuais, e derivação de base_url e desacoplamento de `api_model_name` no fim ainda precisam de escape hatch de closure; dados puros não se realizam; o estilo de closure casa com o modelo `EndpointSpec` do lado custom e com o despacho de pricing por `kind` de `docs/adr/0009`. ④ **Provider da família simples «ausente = default»** (sem spec → aplica closure simples genérico) — fail-silent; `provider_id` errado fabricaria em silêncio um backend simples em vez de errar; cada provider simples se registra explicitamente em uma linha (compartilhando o mesmo closure de build), fail-loud e a tabela é o panorama completo, ao custo de uma linha de declaração.

## Consequences

- **Novo provider embutido cai de «mexer em 4 arquivos 5 lugares» para «adicionar uma linha»**: família simples = uma `ProviderSpec`; família especial = uma + um closure de build; simétrico a adicionar um `EndpointSpec` no lado custom; não se toca mais nos três `_get_or_create_*` de `generation_tasks.py` nem no text factory.
- **As duas cópias de `PROVIDER_ID_TO_BACKEND` se fundem** no campo registry de `ProviderSpec` (cada linha `(provider, media)` declara para qual registry backend mapeia); a drenagem deixa de ser possível no nível da estrutura de dados.
- **Núcleo de construção unit-testável sem DB**: montar à mão um envelope `LoadedConfig` + model_id e assertar os kwargs do backend construído (dual secret kling repassado, bifurcação `backend_type` gemini, derivação de base_url de texto dashscope, desacoplamento `api_model_name` kling), sem subir DB nem mockar resolver; o trecho de carga async se testa com DB em memória (local-substitutable). A validação da tabela embutida tem dois níveis: checagens auto-consistentes da tabela interna como `build` invocável e unicidade de `(provider, media)` no import, fail-fast (mesmo peso leve de `endpoints.py::_validate_video_caps_declarations`); já «todo nome `registry` está no registry de backend de mídia» exige importar todo `lib.{image,video,text}_backends` para assertar — para cenários leves (CLI / migração) não puxarem todos os backends só por importar esta costura, isso vai para unit test (importar o conjunto completo no teste não atrapalha), não para o import.
- **Cache fica no caller**: `_backend_cache` é preocupação de performance da camada de execução do server, não desce para a costura; a costura é sem estado, construção pura — melhor para concorrência e teste.
- **Fronteira de escopo**: a costura só cuida de «criar a instância do backend», sem interferir em execução de tarefa, agendamento de fila, cobrança etc. — persistência de `provider_job_id` em `docs/adr/0007`, agendamento de fila em `docs/adr/0010`, pricing em `docs/adr/0009`, nenhum nesta costura.
- **Ortogonal a futuro marketplace de plugins**: se compartilhar/instalar adaptador de provider de terceiros aterrissar, é epic independente futuro do `ENDPOINT_REGISTRY` do lado custom (`docs/adr/0008` já aponta o caminho para plugin: plugin só aceita `api_key`+`base_url`, e precisa de declaração no estilo «provider embutido» para multi-campo). Este ADR converge o lado **embutido**; o isolamento «não fundir as duas famílias» preserva o lado limpo de encaixe para esse epic, fora deste escopo.
- **status=proposed deste ADR; implementação ainda não aterrissou**: novos nomes `LoadedConfig` / `ProviderSpec` embutido / `backend_assembly` só entram no glossário de `CONTEXT.md` depois de de fato gravados em disco (convenção do projeto: o glossário só registra o que o conceito é agora). Qualquer PR futuro que queira fundir as duas tabelas, introduzir `BackendRequest` unificado, ou devolver a construção embutida a ramos imperativos espalhados precisa deprecar este ADR primeiro.
