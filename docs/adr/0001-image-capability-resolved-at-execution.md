# Capability de imagem (t2i/i2i) só é resolvida na execução; o roteamento de rate-limit do worker usa capability aproximada

Se um shot de storyboard vai por text-to-image (t2i) ou image-to-image (i2i) depende de **haver ou não imagens de referência**; e o conjunto de referências (retratos de personagem/cena/prop citados, e o **storyboard anterior** referenciado por coerência visual) é um snapshot do estado do projeto no **momento em que se começa a desenhar** — em especial na regeneração em lote, o shot N-1 do qual o N depende frequentemente ainda não foi desenhado no enfileiramento. Portanto capability é um fato derivado que só se determina na execução; os dois elos pré-execução — enfileirar e claim do worker — **estruturalmente não podem sabê-la**. Com base nisso decidimos: capability só é resolvida na camada de execução; o enfileiramento não carrega nenhuma informação de provider (o backend snapshot no enqueue já foi removido).

## Consequences

- Ao reivindicar uma tarefa, o worker precisa de um provider só para rate-limit (roteamento de pool); como não tem a capability real, usa de forma unificada `capability="t2i"` para obter um provider **representativo**.
- Só quando o usuário configura **providers diferentes** para t2i e i2i no mesmo projeto a contabilidade de rate-limit cai no pool t2i em vez do pool realmente executado — aproximação conhecida que não afeta a correção da geração (a camada de execução resolve de novo, com precisão, o provider/model realmente usados).
- Esse desvio **não se elimina**: enquanto «t2i/i2i podem ter providers distintos» e «capability só se define na execução» valerem juntos, qualquer rate-limit pré-execução só pode ser aproximado. **Não tente «corrigir» registrando needs_i2i no enqueue/claim** — isso exigiria copiar a lógica de coleta de referências da execução para o scheduler, e na regeneração em lote a resposta no enqueue já estaria errada.
