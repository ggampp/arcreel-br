# Teto de tokens de saída de texto é válvula de segurança não vinculante; truncamento estruturado é erro duro acionável

Planejamento de episódios, geração de roteiro e normalização drama step1, cada um, baixava `max_output_tokens` como **orçamento funcional** para 16000 / 32000, para «economizar / limitar tempo»; mas o volume de saída dessas tarefas é naturalmente limitado por schema e conteúdo — baixar só corta saída normal: planejamento em lote de drama longo (até ~20 episódios com outline) truncava estável no teto, e o caminho estruturado Pydantic do instructor lançava `IncompleteOutputException` que subia como erro não diagnosticável. Decidimos reposicionar `max_output_tokens` como **válvula de segurança não vinculante** (só impede runaway degenerativo do modelo); os três pontos convergem na constante compartilhada única 64000 de `lib/text_backends/base.py` — valor alto o bastante para saída normal de planejamento/roteiro não disparar, só acionando em lote patológico grande ou quando o usuário configurou modelo de capacidade de saída baixa. Em conjunto, elevamos «truncamento» a erro de primeira classe: **saída estruturada** (request com `response_schema`) truncada pelo teto de saída lança `TextOutputTruncatedError` tipado (aponta o modelo de texto atual e sugere trocar por um de maior capacidade de saída); `IncompleteOutputException` do instructor também normaliza para esse erro; **texto livre** (sem `response_schema`) mantém o comportamento log-only de `warn_if_truncated`. Esse erro sai de `generate()` e por natureza short-circuita o loop de retry de validação do planner — reenviar o mesmo request que fatalmente trunca de novo não faz sentido. O planejamento de episódios acrescenta sobre isso o próprio aviso de ajuste manual (diminuir `planning_window_chars` / `planning_max_episodes`, ver `docs/adr/0032`).

## Explicitamente não adotamos

- **Passar `None` e deixar o default do provider**: o default ao omitir `max_tokens` não é uniforme entre providers e não garante alto (relays em especial); e a lógica se inverte — para o provider de validação errar por «não alcança», é preciso pedir ativamente um número grande para ele recusar; `None` é «não pedir nada» e só recebe em silêncio um default possivelmente baixo, truncando sem sinal de trocar de modelo. Com superfície compat Anthropic (`max_tokens` obrigatório), `None` ainda quebra direto. Valor alto explícito é melhor nos três casos.
- **Truncar e re-tentar encolhendo janela/episódios de forma adaptativa**: degradar em silêncio encolhendo o lote contraria «falha explícita, usuário no comando»; encolher a janela ainda pode cortar o arco de enredo em fronteira pior. Preferimos devolver a escolha ao usuário (trocar modelo mais forte ou diminuir as settings sozinho).
- **Tabela de capacidade de teto de saída per-model com cap dinâmico**: o mais aderente, mas exige completar dados externos de todos os providers embutidos e custom, custo de manutenção alto, muito além do escopo desta decisão; o sistema hoje não tem esse registry; a constante alta explícita já basta.

## Consequences

- O teto de saída converge em única fonte de verdade compartilhada; planning / script / normalize referenciam a mesma constante — ajuste só em um lugar.
- Truncamento de saída estruturada é erro tipado duro; truncamento de texto livre mantém aviso soft — dois comportamentos em caminhos separados, superfície limitada a chamadas com `response_schema`.
- O mecanismo de ajuste manual do planner (`planning_window_chars` / `planning_max_episodes`) de fato utilizável depende de settings aceitarem gravar esses valores; os dois formam os dois caminhos de autoajuda após o usuário disparar o erro de truncamento (trocar modelo / diminuir o lote).
- 64000 é válvula de segurança não vinculante, não orçamento preciso: se o usuário configurou modelo com capacidade de saída abaixo disso, o erro de truncamento aparece com mais frequência — é o «falha explícita para trocar de modelo» deliberado, não defeito.
