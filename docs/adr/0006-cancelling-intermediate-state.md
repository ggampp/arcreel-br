# Cancel de tarefa running converge race via estado intermediário cancelling; único caminho de transição de estado

A máquina de estados de tarefa antes só permitia `queued → cancelled` (`task_repo.py:_mark_cancelled` rejeitava duro estados não-queued); na UI o usuário não via entrada para cancelar tarefa running; o `_process_task` do worker também não tinha costura para responder a cancel externo. Ao estender cancel para tarefas running, aparece uma race nova: a API de cancel é «caminho do dia a dia» e exige resposta em segundos (não pode esperar síncrono o finally do worker), mas entre `task.cancel()` no asyncio.Task interno do worker, o lançamento real de `CancelledError` e o finally terminar de escrever o DB há atraso de subsegundo a segundos — nesse intervalo, qual é o status da tarefa no DB? Três opções: (a) a API de cancel grava `cancelled` no DB e o finally do worker checa «já é cancelled → não grava»; (b) a API não mexe no DB e espera o finally do worker gravar; (c) introduzir o estado intermediário `cancelling`: a API grava cancelling, cancela o task local de forma assíncrona, e o finally do worker **só** pode ir de cancelling para cancelled.

Escolhemos (c). (a) espalha a lógica de «quem ganha» em todas as saídas — finally de `_process_task`, `mark_task_succeeded`, `mark_task_failed`, caminho de timeout, falha de resume, todos precisam do mesmo ramo «se já cancelled, preservar»; cada novo caminho de estado final esquece um lugar. (b) o usuário clica cancel e ainda espera 1–2 s no poll para ver a mudança — fere o posicionamento de produto «resposta em segundos». Introduzir `cancelling` converge a race na máquina de estados: `running → cancelling` escrito pela API de cancel, `cancelling → cancelled` pelo finally do worker; outras transições finais (succeeded/failed) **devem** primeiro ver que o atual não é cancelling — essa restrição «não saltar de cancelling para estado final não-cancelled» é garantida no SQL `WHERE` da camada Repository; qualquer novo caminho de finally que passe pelo Repository obedece automaticamente, sem if no caller. O custo de mais um valor no enum de estado é muito menor que manter lógica de «quem ganha» em vários lugares.

## Consequences

- A máquina de estados expande para `queued → running → succeeded | failed | cancelling → cancelled`. `cancelling` é o único não-final que a API externa (cancel) pode escrever ativamente, e só o finally do worker o leva a cancelled. i18n nas três línguas (zh/en/vi) ganha um rótulo de estado `cancelling` (sugestão zh «正在取消…»); o TaskHud do frontend (rótulo de estado + lógica de auto-desaparecer + disponibilidade do botão cancel) precisa reconhecer o novo valor.
- A validação de estado da interface Repository `cancel_task` alarga de «só queued» para «queued ou running»: queued vai direto a cancelled (semântica atual), running vai a cancelling e dispara lookup no dicionário de tasks in-process do worker + `asyncio.Task.cancel()`.
- O finally de `_process_task` do worker, saia por `CancelledError` (sinal de cancel externo) ou por outro `Exception` (incluindo `TimeoutError` de `max_wait` embutido em `poll_with_retry` do backend, `RuntimeError` de falha do provider etc.), ao chamar `mark_task_cancelled` / `mark_task_failed` / `mark_task_succeeded` **não precisa** julgar sozinho «se já houve cancel externo» — o `WHERE status=...` do SQL do Repository faz succeeded/failed a partir de cancelling falharem em silêncio (0 rows affected). Mas o **código de encerramento deve checar se a escrita no repositório surtiu efeito** — o que conta como «surtiu» depende da forma da interface Repository: 0-rows, `None`, `False` ou equivalente «não atualizou» servem; este ADR não amarra a assinatura pública do Repository. Se `mark_task_succeeded`/`mark_task_failed` não surtiu (a tarefa foi para cancelling na race), o finally deve chamar de novo `mark_task_cancelled` para empurrar cancelling → cancelled, senão a tarefa fica presa em cancelling para sempre. Protocolo em uma frase: ao escrever estado final, o worker obedece «0-rows ⇒ vira cancelled» (mantém esse nome de protocolo como âncora de vocabulário para a semântica «não surtiu ⇒ fallback para cancelled», desacoplada da forma concreta de retorno do Repository).
- O canal de sinal de cancel é o `dict[task_id, asyncio.Task]` em memória do worker: o GenerationWorker do ArcReel sempre está no mesmo processo uvicorn que o server principal (ver termo `worker` em `CONTEXT.md`); não há necessidade de cancel cross-process. Se no futuro a arquitetura virar multi-worker (hoje sem plano), será preciso marcar `cancel_requested` no DB + poll do worker; este ADR não reserva isso.
- Semântica de «custo afundado aceito»: cancel faz `task.cancel()` imediato lançando CancelledError; a chamada de API do provider em andamento é interrompida pelo httpx (conexão fechada); o servidor remoto pode continuar gerando; o ArcReel não reembolsa nem persegue o custo já emitido. A semântica atual do UsageTracker «uma chamada, um registro» permanece; no UI, ao cancelar running, deve haver aviso de semântica de custo (⚠️ no botão + tooltip no hover), mas modal de confirm quebraria a resposta em segundos e não entra.
- Não aperte cancelling para «a API só retorna quando já for cancelled»: isso é voltar à opção (b) e fere a resposta em segundos.
- Invariante de transição de estado na camada Repository: **toda escrita de estado final/intermediário deve ser guardada por SQL `WHERE status=...`, impedindo transição indevida**. Em concreto: `mark_task_succeeded` / `mark_task_failed` usam `WHERE status='running'`; `mark_task_cancelled` cobre duas entradas (cancel de queued + fallback do finally do worker em cancelling) com `WHERE status IN ('queued', 'cancelling')`; `mark_task_cancelling` usa `WHERE status='running'`. Essa invariante é a base do protocolo «0-rows ⇒ vira cancelled» — sem o WHERE, escrita concorrente poderia deixar um succeeded atrasado sobrescrever cancelling.
- Este ADR **não** faz o worker embrulhar `execute_generation_task` com `asyncio.timeout()` como timeout externo. Cada video backend já tem timeout em `poll_with_retry` com seu `max_wait` (incluindo estratégias que escalam por duration); timeout lança `TimeoutError` e o finally do worker segue o caminho normal de exceção (marca `failed`), compartilhando a mesma proteção de race «0-rows ⇒ vira cancelled» do cancel. A razoabilidade dos números de `max_wait` de cada backend (se batem com o tempo real de geração do provider) é review independente, rastreada no issue #642, fora do escopo de decisão deste ADR.
