# Fronteiras de decomposição do SessionManager: AgentAccessPolicy com projeção dupla, assembler com I/O simétrico, stream de eventos tipados e SseChannel

O SessionManager de `server/agent_runtime` (~2900 linhas, quase cem métodos) empilhava fisicamente seis responsabilidades mutuamente irrelevantes num único class: regras de acesso e sandbox, montagem de SDK options, broadcast de assinatura, extração de token/cost, ciclo de vida da sessão, serialização de mensagens. A máquina de estados da fronteira de replay vazava no consumidor AssistantService (decodificando as sentinelas `_replay_done` / `_idle` / `_queue_overflow`); regras de acesso só se testavam monkeypatchando métodos privados; broadcast de assinatura e o serviço de eventos de projeto se reimplementavam. Decidimos extrair por responsabilidade modules independentes de interface pequena e implementation profunda, com as fronteiras a seguir: **AgentAccessPolicy** — uma única classe carrega a fonte de verdade das regras «o que o agent pode tocar», com as mesmas regras em duas projeções — compilar settings para a camada de sandbox de kernel, e fornecer julgamento de leitura/escrita/comando por vez para o hook da camada de aplicação; zero I/O, construção pura a partir de caminhos-raiz no nível do processo; a degradação Windows (whitelist de prefixos Bash) se fecha na classe pelo parâmetro de construção `sandbox_enabled`; a remoção de secrets do Bash entra nesta classe (wrap e match de whitelist têm acoplamento mútuo e precisam se localizar); só emite julgamento puro — o encapsulamento SDK e a ordem da cadeia de permissões ficam no adapter fino do lado de gestão de sessão (SDK é dependência opcional; a detecção de ausência só existe no adapter). O nome não é SandboxPolicy — o glossário reserva «sandbox do agent» para a camada de isolamento de kernel; este module também serve hooks de aplicação que não pertencem ao sandbox. **Assembler de Options** — classe que segura dependências e permite I/O; a injeção de credencial (DB → env do subprocesso SDK, transporte e não legado de config) é responsabilidade dela; a decisão de I/O com AgentAccessPolicy segue o mesmo critério — regra estática ⇒ zero I/O; se a natureza da montagem é coletar no campo ao abrir a sessão, I/O é permitido. **Stream de eventos tipados**: o stream de mensagens do SessionManager para o AssistantService permanece um único async context manager; a produção vira eventos semanticamente tipados (lote de replay entregue de uma vez → live item a item → heartbeat → overflow = fim do stream, fim do stream = sinal de reconexão); a costura atômica de replay e assinatura volta para dentro do seam; esta decisão reavalia a proibição de `docs/adr/0005` «não criar sistema de typed event» — o contexto da proibição era o seam parado e o consumidor decodificando sentinelas; com o seam redesenhado, eventos tipados são a forma natural de absorver as sentinelas; o núcleo de 0005 (forma CM, self-check `is_disconnected`, limpeza no `__aexit__`) permanece igual; a formulação de consumo de sentinelas se revisa com a implementação. **SseChannel** converge o broadcast de assinatura do stream de sessão e do de eventos de projeto: a responsabilidade se limita a assinar/desassinar, broadcast, heartbeat ocioso, tratamento de overflow (estratégia parametrizada: mensagem não crítica uma a uma + sinal de overflow vs remover assinante); hooks opcionais de ciclo de vida do primeiro/último assinante; prólogo (replay em buffer / snapshot inicial) não entra no componente — a atomicidade fica garantida pelo lock do consumidor; o endpoint de stream de tarefas já descontinuado (estilo poll de DB) não se conecta. Extração de token/cost e serialização de mensagens viram modules de função pura; ciclo de vida da sessão, expulsão por capacidade e patrulha se mordem mutuamente e compartilham tabela de sessões e locks — ficam no núcleo do SessionManager; SessionActor não muda uma letra (`docs/adr/0028`). Exceto remover o fallback de base_url do provider por variável de ambiente, a decomposição é reorganização estrutural pura; a semântica de comportamento se preserva palavra a palavra.

## Explicitamente não adotamos

- **Degradação Windows como adapter de plataforma** (tendência do relatório de review de arquitetura): rejeitado. As formas de saída das duas plataformas são assimétricas — a rota de kernel produz uma config de start (em runtime larga o Bash); a rota de degradação produz julgamento item a item em runtime — forçar o mesmo interface de adapter gera abstração com metade de no-ops em cada lado; e as regras de caminho realmente compartilhadas são idênticas nas duas plataformas — após a divisão ainda seria preciso um terceiro núcleo compartilhado para carregá-las. A diferença de plataforma se expressa com um ramo booleano de forma mais honesta do que dois adapters semi-vazios. Reviews futuras que proponham de novo o split de adapter usam isto como referência.
- **AgentAccessPolicy como conjunto de funções puras**: cada função precisaria de 5+ parâmetros de caminho-raiz; a assinatura explode e o caller ainda junta os parâmetros sozinho — a complexidade só se move da classe para o ponto de chamada.
- **SseChannel inclui o prólogo** (callback de «função produtora de prólogo» na assinatura): replay em buffer e snapshot de varredura ao vivo não têm uma linha de implementação em comum; parametrizar é abstração falsa — o componente não fica mais profundo, só ganha uma camada de encaminhamento.
- **Interface de stream em duas chamadas** (primeiro lista de replay, depois assinar live): entre as duas chamadas se perde mensagem; o motivo do desenho de stream único é justamente costurar replay e assinatura sem costura no mesmo lock; fechar a costura exigiria cursor cross-call ou lock compartilhado — a interface ficaria mais complexa.
- **Injeção de credencial dentro de AgentAccessPolicy** (classificando por «mesmo guarda-chuva de higiene de secret»): classificar por tema de ADR é pior do que classificar por forma de dependência — injeção lê DB, remoção é zero I/O; meter na mesma classe destrói a base de construção pura e testável da segunda.

## Consequences

- AssistantService deixa de perceber qualquer sentinela; sentinelas in-band viram mecanismo interno de SseChannel. `docs/adr/0005` se revisa em sincronia quando o stream de eventos tipados aterrissa (descreve o estado atual, sem cadeia de substituição em patch).
- Testes de regra de acesso saem de monkeypatch de método privado/variável de ambiente para assert allow/deny alimentado por parâmetro de construção; asserções se preservam palavra a palavra no período de migração; limpeza de redundância é pós-trabalho independente.
- O cerco de variáveis de ambiente de secrets de provider (asserção no startup, override com valor vazio, remoção Bash) se qualifica como mecanismo permanente — as duas causas «transporte» (subprocesso SDK só autentica por env) e «cerco» (ambiente do processo pai é entrada externa) não somem com a config no DB; não se limpam como dívida técnica.
- CONTEXT.md ganha entradas AgentAccessPolicy e SseChannel com a implementação; o _Avoid_ da entrada AgentAccessPolicy anota SandboxPolicy.
