# Multi-secret de provider embutido: colunas tipadas nomeadas pela chave do registry; sem JSON / subtabela / concatenação

Kling é o primeiro provider embutido que precisa de **duas strings secret** (`access_key` + `secret_key`, auth JWT HS256). `docs/adr/0008` já fixou «credencial multi-campo só via `PROVIDER_REGISTRY.required_keys: list[str]` de provider embutido», mas isso é só a **camada de declaração** — o **armazenamento** de credencial de provider embutido está na tabela `provider_credential` (multi-credencial + active manual de `docs/adr/0016`), com colunas fixas `api_key` / `credentials_path` / `base_url`; `overlay_config()` também só move essas três — não cabe o segundo secret. Os providers «multi-campo» existentes na prática não são duas strings secret: gemini-vertex é um único caminho de arquivo de service account (coluna `credentials_path`); o resto é um único `api_key`.

Decidimos **adicionar à tabela `provider_credential` colunas tipadas nomeadas pela chave do registry** (`access_key`, `secret_key`, Text nullable); `overlay_config()` produz config com o mesmo nome de coluna (`config["access_key"] = ...`), de modo que **nome da chave no registry = nome do campo no formulário = nome do parâmetro de construção do backend = chave do dict de config** são o mesmo nome de ponta a ponta, sem camada de tradução coluna↔key; mascaramento reutiliza `mask_secret` coluna a coluna. **Explicitamente não adotamos**: ① concatenar `access_key:secret_key` em um único `api_key` e depois desmontar (`docs/adr/0008` já rejeitou — quebra a semântica de exibição de chave única de `mask_secret`); ② coluna JSON genérica `extra` (`docs/adr/0016` já achou «campo JSON único com read-modify-write concorrente complexo» e exigiria pipeline de mascaramento por campo); ③ subtabela de campos de credencial (uma tabela + join por um provider — volume mecânico máximo); ④ reutilizar KV `ProviderConfig` para secrets Kling (contorna `docs/adr/0016`: não participa da troca de active multi-credencial, o julgamento de ready não vê, abriria exceção no resolver).

É trade-off YAGNI: hoje só Kling precisa de duas strings secret (AKSK do visual CV Volcano não é provider embutido deste lote; Vertex é caminho de arquivo único). JSON/subtabela por um único provider não compensa; coluna tipada também continua o precedente existente de «coluna tipada dedicada a provider» como `credentials_path` na tabela.

## Consequences

- **Risco de inchaço de coluna aceito de forma explícita**: `access_key`/`secret_key` em `provider_credential` são NULL para todos os providers exceto Kling (colunas esparsas); `api_key` e `access_key` coexistem como colunas quase sinônimas. Explicado por este ADR e pela declaração no registry; não tratar como campo morto a limpar.
- **Gatilho de refatoração**: ao aparecer o **terceiro** provider embutido que precise de ≥2 campos secret (especialmente com nomes de campo diferentes), reavaliar upgrade para coluna JSON genérica `extra` ou subtabela de campos de credencial — aí a refatoração tem base e este ADR vira superseded.
- **Mantém as fronteiras existentes**: herda `docs/adr/0008` (não contornar com string concatenada; multi-campo só provider embutido) e `docs/adr/0016` (credencial em tabela dedicada + colunas tipadas, sem JSON). Qualquer PR futuro que queira JSON/subtabela/concatenação precisa deprecar este ADR primeiro.
- **Mudanças convergem na camada de credencial**: modelo + uma migração additive de colunas nullable (sem backfill; as duas colunas não entram em nenhum `WHERE`); `CredentialRepository.create/update`; `overlay_config`; rotas CRUD de credencial (body do request + resposta com mascaramento por campo + metadados de campo); formulário de credencial na página de settings (render por `required_keys`). Teste de conectividade próprio do provider (ex. probe de assinatura JWT Kling) não fica nesta camada — acompanha a integração de cada provider.
