# Edições do Agent em JSON de projeto ficam em ferramentas MCP in-process; Write/Edit/Bash nus são sempre deny

Hoje o Agent pode usar `Write`/`Edit` nus (ou até Bash com `echo>`/`sed`/`python -c`) para alterar direto `scripts/*.json` e `project.json`, passando só por um hook PreToolUse de **sintaxe JSON** — erros estruturais (`duration_seconds` fora da faixa, falta de `image_prompt`, inconsistência shots↔duration em `ReferenceVideoUnit`) gravam em disco e contornam a entrada unificada `_write_script_unlocked` (ADR-0002). Esse desvio torna o «ponto de guarda único» falso. Decidimos recolher **toda** escrita do Agent em dados JSON de projeto em um conjunto de ferramentas MCP in-process e, fora delas, **proibir** escrita bruta de bytes nesses dois tipos de arquivo, para que a validação estrutural do ADR-0002 tenha de fato um único ponto forçado.

Conjunto de ferramentas (todas MCP `arcreel` in-process, no processo do server, não no sandbox do agent):

- `patch_episode_script` — edição em lote de campos: passa `script` + mapa `{segment_id/scene_id/unit_id/shot_id: {caminho do campo: valor}}`, altera de uma vez vários storyboards × vários campos (edição única = mapa de comprimento 1), **localiza por `segment_id`/`scene_id`/`unit_id`/`shot_id`** (igual a `update_scene_asset`; índices numéricos só são convenção na geração; em runtime a ordem é posição no array; compose/`resolve_episode_from_script` não resolvem índice), genérico a todos os modos de conteúdo/geração. Setter puro; atômico all-or-nothing — o lote inteiro reutiliza `patch_field` um a um no mesmo contexto `locked_script`; qualquer edição ilegal não grava nada (atomicidade sustentada por «só grava se sair normal / exceção não grava / guarda não-piorar antes de gravar» do `locked_script`, sem nova pipeline de transação).
- `insert_segment` / `remove_segment` / `split_segment` — inclusão/remoção/divisão estrutural, cobrindo os três modos (modo reference age em `video_units`/`shots`). **ids estáveis, sem reordenar**; inserção/split **por modo** emitem id novo com sufixo `_{subíndice}`: segments/scenes de narration/drama usam `E{ep}S{n}`, units de reference usam `E{ep}U{n}` (ver definições de `segment_id`/`scene_id`/`unit_id` em `script_models.py`; o prefixo não pode unificar em `S`, senão reference falha na validação Pydantic).
- `patch_project` — add+update de `project.json` (por table+name), **substitui** `add_assets.py` (script removido; o subagent `analyze-assets` passa a chamar esta ferramenta, eliminando também a frágil chamada CLI-JSON de uma linha).
- `generate_episode_script` — geração de episódio inteiro, passando a **gravar via `_write_script_unlocked`** (em vez do `json.dump` nu que o `ScriptGenerator` usava).

Força (duas camadas):

- **Subprocesso Bash** (Linux/macOS, nível de kernel): `sandbox.filesystem.denyWrite` cobre o diretório `scripts/` e `project.json`. A documentação do SDK (sandboxing.md) deixa claro que `denyWrite` é OS-level (Seatbelt / bwrap profile) e vale para **todos os subprocessos no sandbox (incluindo Bash e seus filhos)** — fecha o desvio `echo>`/`sed`/`python -c`. Preferimos `denyWrite` a «empurrar regra Edit-deny»: o primeiro é campo documentado de write-deny, no mesmo passthrough `filesystem` que o `denyRead` existente, sem depender de regras Edit allow/deny serem derivadas pelo SDK no profile FS do Bash (comportamento não garantido por escrito).
- **Write/Edit embutidos** (todas as plataformas): ferramentas de arquivo embutidas não passam pelo sandbox (passam pelo sistema de permissões); o hook `_check_write_access` recusa `scripts/*.json` + `project.json`. Mesma origem do denyWrite acima (os mesmos dois caminhos), formando a segunda camada.
- Toda escrita de roteiro funiliza em `_write_script_unlocked`: herda a semântica «não piorar» do ADR-0002 + recálculo de metadata (`total_scenes`/`estimated_duration_seconds`) + lock + consistência filename↔episode. `project.json` passa por `update_project(_mutate)` e, dentro da mutation, aplica **a mesma validação «não piorar»** no payload resultante (dados sujos históricos já ilegais antes seguem; só recusa se este upsert transformar project legal em ilegal) — mesma origem do `_guard_no_worse` da entrada unificada de roteiro; se virasse «resultado deve ser absolutamente legal», projetos com problemas legados (ex.: `style` vazio) tornariam o caminho `patch_project` inteiro inutilizável (o antigo `add_assets.py` reportava erro de validação e mesmo assim não bloqueava a escrita).

## Consequences

- Ferramentas MCP in-process rodam no processo do server, **fora do sandbox do agent**, logo o profile FS write-deny não as restringe e elas gravam normalmente; após remover `add_assets.py`, **não resta nenhum Bash legítimo no sandbox que escreva `scripts/*.json`/`project.json`** (`split_episode` escreve em `source/`, compose escreve saídas de vídeo, nenhum dos dois toca), então o write-deny de kernel não fere em falso.
- **Fallback sem sandbox** (Windows, ou falha de detecção bwrap no Linux): o bloqueio de kernel some; volta `_check_write_access` deny (Write/Edit, todas as plataformas) + o `_WINDOWS_BASH_PREFIX_WHITELIST` existente (só libera `python .claude/skills/`, ffmpeg, ffprobe; qualquer `echo>`/`sed`/`python -c` já não está na lista). Revisado: após remover `add_assets.py`, nenhum script liberado em `python .claude/skills/` escreve `scripts/*.json`/`project.json` (split → `source/`, compose → vídeo, peek só leitura), logo o fallback sem sandbox não precisa de defesa extra especial.
- **denyWrite de kernel em smoke real**: `denyWrite` usa o mesmo passthrough `filesystem` que `denyRead` (este já protege `.env` etc. em produção — mecanismo confiável). A recusa de escrita de kernel em subprocessos Bash é o comportamento do mesmo campo prometido na doc do SDK; após aterrissar, recomenda-se um live smoke test (com sandbox ativo, `echo > scripts/x.json` no Bash deve ser recusado pelo kernel, enquanto a ferramenta MCP grava ok) para promover a `accepted`.
- **`patch` não invalida `generated_assets`** (setter puro de campos). O sistema não tem detecção de frescor/stale (`status` só se calcula pela existência de caminhos), então mudar `image_prompt` sem regenerar gera o stale silencioso «prompt novo + imagem antiga + status=completed». Trade-off consciente: o cenário típico é «mudar prompt **e** regenerar»; regen sobrescreve o asset; invalidação automática exigiria hardcodar a cadeia campo→asset no patch e poderia apagar imagens que o usuário quer manter. O custo fica na disciplina do agent profile «mudou prompt → regenera» + este ADR. Alternativa mais leve — ao mudar campos críticos resetar `generated_assets.status` para `pending` (sem apagar caminhos) — **não adotada**: edição de JSON do roteiro e ciclo de vida do asset ficam **desacoplados**; patch não declara nada sobre estado de asset; gerar/regenerar é ação explícita independente.
- **Ferramentas estruturais (split/remove) limpam `generated_assets` dos storyboards afetados**: ao contrário da edição de campos, mudança estrutural altera identidade do storyboard (`E1S3` vira dois; o asset antigo não tem dono razoável), então é obrigatório esvaziar e voltar a pending.
- **Texto de retorno** da ferramenta é agent-facing (isento de i18n); **nome de exibição** é user-facing e deve ser registrado em `ARCREEL_MCP_TOOL_IDS` com `tool_name_<id>` nas três línguas (zh/en/vi).
- Mesma origem do ADR-0002: este ADR cumpre a promessa de «recolher a face de escrita nua do Agent». A semântica exata do split em reference_video (cortar unit ou shots) fica como detalhe de implementação; a restrição é o resultado satisfazer a validação `duration==sum(shots)` de `ReferenceVideoUnit` (a validação estrutural `_select_model` já roteia `video_units` para `ReferenceVideoScript`, e o model_validator dela segura). O recálculo de metadata em `_write_script_unlocked` (`total_scenes`/`estimated_duration_seconds`) antes só reconhecia `segments`/`scenes` (`video_units` caía no fallback de segments e zerava); #604 já unificou esse critério com o mesmo `script_editor.resolve_items` de `_select_model` — três lugares (validação estrutural / núcleo de edição / recálculo de metadata) compartilham um único discrimine.

## Limite da semântica «não piorar» (iteração de causa-raiz pós-#604)

O PR #608 aterrissou o recolhimento de ferramentas deste ADR sobre o «não piorar» do ADR-0002, mas várias rodadas de code-review acharam o mesmo padrão: o «não piorar» generalizou em silêncio de estratégia concreta para «clima de tolerância», e helpers fora da garganta de escrita, caminhos de leitura, sync entre episódios e whitelist do agent reutilizaram a atitude «dados sujos → degradar», gerando silent-noop / silent-overwrite. Esta iteração de causa-raiz trava o limite:

- **«Não piorar» só existe em dois gargalos**: `_guard_no_worse` em `_write_script_unlocked` na escrita do roteiro (estrutura do script, via `_select_model` + Pydantic ValidationError); diff de error-set dentro de `_mutate` em `upsert_assets` (project.json, via diferença do conjunto de errors de `DataValidator.validate_project_payload`). Fora desses dois pontos, **nenhum** helper/caller pode carregar estratégia local de «e se os dados estiverem sujos».
- **Fora do gargalo, sempre fail-loud**: `resolve_items` lança `ScriptEditError` se a chave do array de storyboards existe mas não é list (já é assim); `batch_update_scene_assets` fail-loud com `KeyError` se o id não bate (neste PR); no recálculo de metadata de `_write_script_unlocked`, `duration_seconds=None` é ausência, não crash; `get_storyboard_items` passa por `resolve_items` para alinhar o tipo de exceção de dados sujos (não mais `list(None)` → TypeError genérico).
- **Degradação é decisão explícita do caller**: `versions.py::_sync_storyboard_metadata` aperta de `except Exception` para `except ScriptEditError` + warning com nome do episódio + continue (degradação de sync cross-episode com script sujo, com sinal observável); exceções inesperadas sobem a 5xx no router. No caminho de leitura, `_resolve_items_or_warn` já faz warning com dados sujos; missing key retorna `[]` sem warning (rascunho vazio é estado inicial legal). **Proibido sucesso sem sinal** — qualquer caminho de degradação precisa de warning.
- **silent drop da whitelist do agent vira feedback explícito**: `upsert_assets` retorna dict de diagnóstico (added / merged / dropped_fields / dropped_legacy); a ferramenta `patch_project` monta texto dizendo ao agent «os campos abaixo estão fora do escopo editável do agent (reference_image / sheet_field) e foram ignorados» / «os campos legados abaixo foram descontinuados (type / importance)», para o LLM não insistir em campos que serão descartados; o prompt do subagent `analyze-assets` passa a skip estrito do que já existe (filtrar antes de chamar patch_project), eliminando a contradição «não sobrescreve» vs «pode revisar».
- **Roteamento prioriza forma dos dados**: `resolve_kind` deixa de priorizar `generation_mode` e passa a rotear por existência das chaves de topo `video_units` / `segments` / `scenes` + `content_mode` auxiliar. Motivo: em estado intermediário de partial migration (config já reference, dados ainda em segments), a lógica antiga fazia `generation_mode` vencer sozinho e o script inteiro ficava inalcançável para todas as ferramentas MCP de edição — o agent via «id não encontrado» sem pista.
- **Fronteira de responsabilidade das ferramentas**: `_set_nested` de `patch_episode_script` **permite escrever** se a folha (último segmento) não existe (campos optional que o LLM esqueceu, ex. `video_prompt.note`, o agent deve poder completar sem ser forçado a remove+insert regenerando o episódio); se o nó pai (segmento intermediário do caminho) não existe, continua fail-loud (bloqueia typo); `split_segment` preserva `generated_assets` de `parts[0]` (âncora), alinhado à semântica de preservar asset âncora de `insert_segment` — usar split como insert por engano não perde mais assets já gerados.

Princípio transversal: **ao endurecer fail-loud, enumerate primeiro a matriz 2D** (leitura/escrita × chave ausente/chave suja × validate/no-validate) e decida célula a célula; não empurre a estratégia «não piorar» («não introduzir erro novo na camada de validação estrutural») para helpers sem noção de before/after (recálculo de metadata, key lookup, tratamento de exceção) — nesses cenários, degradar dados sujos é responsabilidade explícita do caller, não comportamento padrão do helper.

## Limitação conhecida do estado intermediário de partial migration (opção C)

O item «roteamento prioriza forma dos dados» só mudou `resolve_kind` (compartilhado por validação estrutural / núcleo de edição / recálculo de metadata); três **callers de caminho de geração** ainda discriminam priorizando `generation_mode` e não migraram:

| caller | critério | comportamento em partial migration |
|---|---|---|
| `enqueue_videos.py::_is_reference_script` | `generation_mode == "reference_video"` | ramo reference lê `video_units` vazio e lança `ValueError(f"第 {episode} 集 video_units 为空：{script_filename}")` |
| `storyboard_sequence.py::get_storyboard_items` | early return `[]` se `generation_mode == "reference_video"` | storyboard / grid / cost_estimation veem episódio vazio; UI: «nenhuma tarefa para gerar» |
| `status_calculator.py::_select_content_mode_and_items` | pega `video_units` se `generation_mode == "reference_video"` | progress / contagem de scenes = 0; frontend: «projeto vazio» |

No estado intermediário de partial migration (config já `generation_mode=reference_video`, dados de storyboard ainda em `segments`), os dois critérios divergem: ferramentas MCP de edição (por forma dos dados) veem segments e editam ok; os três callers acima (por generation_mode) julgam vazio.

**Decisão**: o estado intermediário de partial migration é **estado anômalo**, não forma legal suportada. A semântica de produto exige que «mudar `generation_mode` implica migrar os dados de storyboard para a chave de topo correspondente» seja uma migração completa e atômica; parar no meio é erro operacional — o sistema não garante disponibilidade funcional nesse meio-termo. Este issue só documenta o trade-off e **não altera o comportamento de runtime dos três callers**.

**Motivo**: migrar todos os callers para `resolve_kind` (opção A) forçaria o inverso — projetos em partial migration (config reference, dados em segments) nunca chegariam ao caminho de geração reference, ou seja, a forma dos dados anularia a intenção de config do usuário; detectar meio-termo + erro diagnóstico (opção B) exige espalhar detecção de estado em vários callers e só troca «vazio» por «erro» — sintoma. Partial migration é canto raro; fechar com «trade-off documentado» e deixar o conserto de comportamento para refatoração futura tem menor custo e não introduz novos ramos de runtime.

**Destino do conserto de comportamento**: refatoração que eleva reference_video a tipo de conteúdo de topo (issue #618). Aí `generation_mode=reference_video` e a chave de topo `video_units` ficam 1:1, config e forma dos dados não se desencontram mais, o estado intermediário some pela raiz e a inconsistência desses três critérios some junto.
