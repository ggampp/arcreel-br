# Validação ao salvar roteiro usa semântica «não piorar»; hot path de reescrita de assets isento

A validação estrutural do roteiro (formas de `segment`/`scene`/`unit`, faixas de `duration`, campos obrigatórios), depois de extraída para função pura, só era chamada na fronteira de arquivo; o caminho de escrita em disco não validava — dados sujos não falhavam na gravação, `load_script` só faz `json.load` e também não falha, e a explosão só vinha no fundo do worker ao parsear. Decidimos antecipar esse validador estrutural (uma definição em função pura) para a entrada unificada de escrita Python `_write_script_unlocked`, mas **sem** adotar «sempre raise estrito»: a escrita só é recusada quando «antes era válido ∧ depois é inválido» (esta gravação introduziu erro estrutural novo); roteiros legados que já eram inválidos antes seguem liberados; e o hot path de reescrita de assets que só mexe em `generated_assets` (`update_scene_asset` / `batch_update_scene_assets` / `update_character_sheet` / reescrita de tarefas de vídeo de referência) **pula** a validação por completo. O objeto validado é o modelo Pydantic de estrutura (escolhido por `generation_mode`/chaves de topo: `Narration`/`Drama`/`ReferenceVideoScript`), **não** o `DataValidator` sensível a FS — este lê disco e rejeitaria rascunhos legítimos incompletos (storyboard ainda não gerado).

## Consequences

- Às vezes o save aceita um roteiro já ilegal (já quebrado antes). É intencional: o guarda existe para «não deixar esta edição trazer sujeira para o sistema», não para carregar o fardo de legado da evolução de schema; senão o usuário editando um roteiro antigo «válido na época, fora do schema atual» tomaria 400 de repente sem a edição atual ser ilegal. Quando `load_script` não pré-carrega `before` (ex.: normalize que chama `save_script` direto), o script saído é recalculado completo e a validação estrita basta.
- Pular validação no caminho de reescrita de assets significa que o worker anexando `generated_assets` a um roteiro legado ilegal não morre em cascata. Motivo: performance + semântica — hot paths de alta frequência, só escrevem campos de runtime `SkipJsonSchema`, a estrutura não piora por isso, não faz sentido revalidar o script inteiro a cada vez.
- Falha de validação aparece **na escrita** (caminho manual retorna erro), não só depois de enfileirar e explodir na execução.
- Roteiro/`project.json` têm três faces de escrita: API Python (`save_script` etc., coberta por este ADR), ferramentas de geração do Agent (`text_generation`→`ScriptGenerator`, já com validação Pydantic na geração), e **`Write`/`Edit` nus do Agent**. A última hoje só passa pelo hook PreToolUse de sintaxe JSON (`json.loads` + aspas curvas); erros estruturais ainda gravam em disco e contornam a entrada unificada deste ADR. Já decidimos **recolher isso no ProjectManager**: negar `Write`/`Edit` nus do Agent em `scripts/*.json` + `project.json`, e transferir para ferramentas que passam por `_write_script_unlocked`, de modo que a validação estrutural tenha de fato um único ponto forçado. Esse affordance substituto (granularidade/protocolo/ajuste de profile/escopo exato do deny/tratamento de raw write no lado da ferramenta) é feature independente a desenhar à parte; este ADR não a expande.
- **Não «apertar» para sempre raise estrito**: isso faria editar roteiro antigo voltar a 400 e carregaria o hot path com validação full a cada reescrita — exatamente o que esta decisão evita.
- Validação no enfileiramento é eixo independente: este ADR cobre «escrever em disco»; validação estrutural no enqueue (agnóstica de provider) e validação de capacidade (duration↔supported_durations, resolvida na execução, ver princípio em `docs/adr/0001`) caem em outro lugar, dependendo da convergência da resolução de provider (#599) primeiro.
